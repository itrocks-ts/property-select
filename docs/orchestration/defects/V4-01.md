# V4-01: Expired request autosave replaces the documented session response

## Status and impact

**FIXED (author), awaiting independent RETEST-V4-1 / P2**, found independently during V4 on 16 October 2026.
Blocks V4 and L5.
Primary owner: `@itrocks/fastify`; review `fastify-file-session-store`, `list` and framework composition together.
No product correction was made by the verifier. The [author correction](../reports/FIX-V4-1.md) now preserves 410
through the Fastify session bridge; the original failed V4 gate remains blocked until independent retest.

The public list [state API](../../../../list/README.md) documents HTTP 410 for ended sessions.
`SelectorStateAction` catches `SESSION_STALE` and prepares that response. However, the Fastify session response hook
attempts autosave of the same obsolete request and replaces it with HTTP 500 and a `SESSION_STALE` JSON body.
The browser `HttpStateStore` handles 410 as “The selector session has ended. Reload the page.”
For the observed 500 it instead reports “Unable to save selector state (500). Try again.”
Retry retains the obsolete generation, so this advice does not recover the mounted selector.

Data protection remains intact in this reproduction: obsolete state is not resurrected, old-generation new requests
receive 410, and a newly established session remains writable. This is an HTTP lifecycle/error-contract defect,
not evidence of lost isolation or resurrected data.

## Independent reproduction

Run from showtime, with installed dependencies and the existing synthetic database on 13316:

```bash
node node_modules/@itrocks/property-select/docs/orchestration/environment/checks/V4-revoke.mjs
```

Use normal escalation if local listeners require it. The driver starts and stops only its owned application on 13911,
with ownership directory `/tmp/property-select/V4-revoke` and a persistent synthetic session secret kept outside Git.
The fixture wraps the public `listStateDependsOn` transaction port with a one-request delay, then delegates to the
actual public `sessionTransaction`. It neither fabricates session state nor replaces the production HTTP action.

1. Establish a real session through `/country`; GET the production state endpoint to obtain revision and generation.
2. Arm a fixture gate, issue a PUT to `/property-select/state/json` and wait until its acquired session reaches the
port.
3. Revoke that session through the fixture's real `session.destroy()`, or expire its actual cookie date.
4. Release the gate. Expect 410; observe 500 in **both** cases.
5. Send another request with the obsolete generation: 410. Restart the actual server with the same session directory
   and secret, establish the new session through `/country`, then read: obsolete state absent. Fresh write: 200.
